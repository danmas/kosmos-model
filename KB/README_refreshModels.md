# Автоматическая синхронизация моделей

Система автоматически синхронизирует списки моделей от провайдеров, поддерживая их в актуальном состоянии без потери ручных настроек.

## Общая информация

- **Периодичность:** Синхронизация происходит при запуске сервера и далее каждые 8 часов
- **Файл конфигурации:** `data/available-models.json`
- **Принцип работы:** Добавляются новые модели, устаревшие отключаются (но не удаляются), ручные настройки сохраняются

## Поддерживаемые провайдеры

Автоматическая синхронизация моделей поддерживается для следующих провайдеров:

- ✅ **Groq** — все модели
- ✅ **OpenRouter** — только бесплатные модели
- ✅ **Direct** — все модели для каждого уникального `base_url` (OpenAI-совместимые API)

---

### ✅ Groq (`refreshGroqModels()`)

**API эндпоинт:**
```
GET https://api.groq.com/openai/v1/models
Authorization: Bearer {GROQ_API_KEY}
```

**Особенности:**
- Синхронизирует **все модели** от Groq
- Требует наличие `GROQ_API_KEY` в `.env`
- Если сервис не настроен, синхронизация пропускается с предупреждением

**Формат внутреннего ID:**
```
groq-{model_id}
```
Например: `groq-llama-3.3-70b-versatile`

**Автоматическое определение параметров:**
- **Context window:** Извлекается из имени модели:
  - Паттерн `-(\d+)k` → умножается на 1024 (например, `-128k` → 131072)
  - Паттерн `-(\d{4,5})` → используется как есть (например, `-8192` → 8192)
  - По умолчанию: `8192`
- **Fast:** Автоматически устанавливается в `true`
- **Visible name:** `GROQ → {model_id}`

**Пример добавляемой модели:**
```json
{
  "id": "groq-llama-3.3-70b-versatile",
  "provider": "groq",
  "name": "llama-3.3-70b-versatile",
  "visible_name": "GROQ → llama-3.3-70b-versatile",
  "context": 131072,
  "fast": true,
  "user_type": null,
  "enabled": true,
  "added_at": "2024-01-15T10:30:00.000Z"
}
```

**Логика синхронизации:**
1. Запрашивается список всех моделей от Groq API
2. Создается Map активных моделей с ключом `groq-{model_id}`
3. Для существующих локальных моделей Groq:
   - Если модель отсутствует в удаленном списке → отключается (`enabled: false`)
   - Если модель присутствует → сохраняются все ручные настройки
4. Для новых моделей из API:
   - Если модели нет локально → добавляется с параметрами по умолчанию
   - Если модель уже есть → не трогается (сохраняются настройки)

---

### ✅ OpenRouter (`refreshOpenRouterModels()`)

**API эндпоинт:**
```
GET https://openrouter.ai/api/v1/models
```
(API ключ не требуется для получения списка моделей)

**Особенности:**
- Синхронизирует **только бесплатные модели**
- Фильтрация по критерию: модель содержит `:free`, `-free` или заканчивается на `:free`
- Не требует API ключ для синхронизации списка

**Формат внутреннего ID:**
```
or-{model_id}
```
Символы `:` заменяются на `-` для совместимости.

Например: `openai/gpt-3.5-turbo:free` → `or-openai-gpt-3.5-turbo-free`

**Автоматическое определение параметров:**
- **Context window:** Используется `context_length` из API ответа, по умолчанию `32768`
- **Free:** Автоматически устанавливается в `true`
- **Visible name:** `OpenRouter → {model.name || model.id}`

**Пример добавляемой модели:**
```json
{
  "id": "or-openai-gpt-3.5-turbo-free",
  "provider": "openroute",
  "name": "openai/gpt-3.5-turbo:free",
  "visible_name": "OpenRouter → GPT-3.5 Turbo",
  "context": 16385,
  "user_type": null,
  "enabled": true,
  "free": true,
  "added_at": "2024-01-15T10:30:00.000Z"
}
```

**Логика синхронизации:**
1. Запрашивается список всех моделей от OpenRouter API
2. Фильтруются только бесплатные модели (содержат `:free` или `-free`)
3. Создается Map активных бесплатных моделей с ключом `or-{model_id}`
4. Для существующих локальных моделей OpenRouter:
   - Если модель отсутствует в актуальном бесплатном списке → отключается (`enabled: false`)
   - Если модель присутствует → **НЕ ТРОГАЕТСЯ** (сохраняются все ручные настройки)
5. Для новых бесплатных моделей из API:
   - Если модели нет локально → добавляется с параметрами по умолчанию
   - Если модель уже есть → не трогается

### ✅ Direct (Z.AI / Custom / Together / и др.)

**API эндпоинт:**
```
GET {base_url}/v1/models
Authorization: Bearer {API_KEY}
```

**Особенности:**
- Синхронизирует модели для каждого уникального `base_url` отдельно
- Требует наличие `base_url` и `api_key` в конфигурации модели
- Поддерживает формат `env:VAR_NAME` для API ключей
- Если `/v1/models` не поддерживается или возвращает ошибку — тихо пропускается (без критических ошибок)

**Формат внутреннего ID:**
```
direct-{hostname}-{model_id}
```
Например: `direct-api-together-xyz-meta-llama-llama-3-3-70b-instruct-turbo`

**Автоматическое определение параметров:**
- **Context window:** Используется `context_length` из API ответа, или извлекается из имени модели (паттерны `-(\d+)k` или `-(\d{4,5})`), по умолчанию `8192`
- **Visible name:** `{ProviderName} → {model.name || model.id}` (ProviderName извлекается из hostname)
- **Base URL:** Сохраняется из исходной модели
- **API Key:** Используется формат из первой модели с тем же `base_url`

**Пример добавляемой модели:**
```json
{
  "id": "direct-api-together-xyz-meta-llama-llama-3-3-70b-instruct-turbo",
  "provider": "direct",
  "name": "meta-llama/Llama-3.3-70B-Instruct-Turbo",
  "visible_name": "Together → Llama-3.3-70B-Instruct-Turbo",
  "base_url": "https://api.together.xyz/v1",
  "api_key": "env:TOGETHER_API_KEY",
  "context": 131072,
  "user_type": null,
  "enabled": true,
  "added_at": "2024-01-15T10:30:00.000Z"
}
```

**Логика синхронизации:**
1. Находятся все модели с `provider: "direct"` и `base_url`
2. Модели группируются по уникальным `base_url`
3. Для каждого `base_url`:
   - Получается API ключ из первой модели с этим `base_url` (поддерживается `env:VAR_NAME`)
   - Запрашивается `{base_url}/v1/models` (или `{base_url}/models` если base_url заканчивается на `/v1`)
   - Если запрос успешен:
     - Создается Map активных моделей с ключом `direct-{hostname}-{model_id}`
     - Обновляются существующие модели для этого `base_url` (отключаются устаревшие)
     - Добавляются новые модели
   - Если запрос не удался (404, таймаут, ошибка авторизации) — тихо пропускается без ошибки
4. Сохраняются все изменения в `available-models.json`

**Обработка ошибок:**
- **404 Not Found:** `/v1/models` не поддерживается — пропускается
- **401/403 Unauthorized:** Ошибка авторизации — пропускается
- **Таймаут:** Превышено время ожидания (10 секунд) — пропускается
- **Другие ошибки:** Тихая обработка, пропускается без критических ошибок

**Требуемые поля для direct моделей:**
```json
{
  "id": "direct-{unique-id}",
  "provider": "direct",
  "name": "model-name",
  "base_url": "https://api.example.com",
  "api_key": "env:ZAI_API_KEY"  // или прямой ключ
}
```

**Ручное добавление:**
Модели провайдера `direct` также могут быть добавлены вручную через:
- UI интерфейс (`/models.html`)
- Прямое редактирование `available-models.json`
- API эндпоинт `/api/models/add`

## Общая логика работы

### Алгоритм синхронизации (общий для всех провайдеров)

**Для Groq и OpenRouter:**
```
1. Запрос к API провайдера
   ↓
2. Создание Map активных моделей (ключ = внутренний ID)
   ↓
3. Обновление существующих локальных моделей:
   - Если модель отсутствует в Map → enabled: false
   - Если модель присутствует → сохраняются все настройки
   ↓
4. Добавление новых моделей:
   - Если модели нет локально → добавляется с дефолтными параметрами
   - Если модель уже есть → пропускается
   ↓
5. Сохранение в available-models.json
```

**Для Direct (специальная логика):**
```
1. Группировка моделей по base_url
   ↓
2. Для каждого base_url:
   - Получение API ключа
   - Запрос к {base_url}/v1/models
   - Если успешно → обработка как выше
   - Если ошибка → тихо пропускается
   ↓
3. Сохранение всех изменений
```

### Что сохраняется при синхронизации

✅ **Сохраняются (не перезаписываются):**
- `user_type` (ручные метки типа CHEAP/FAST/RICH)
- `enabled` (если модель была вручную отключена, она останется отключенной)
- Все кастомные поля, добавленные вручную
- `visible_name` (если был изменен)

❌ **Перезаписываются:**
- Только для новых моделей (при первом добавлении)
- Параметры существующих моделей не изменяются

### Обработка устаревших моделей

- Устаревшие модели **не удаляются** из файла
- Они помечаются как `enabled: false`
- Это позволяет:
  - Сохранить историю использования
  - Восстановить модель вручную, если она вернется в API
  - Не потерять кастомные настройки

## Запуск синхронизации

### Автоматический запуск

Синхронизация запускается автоматически:

1. **При старте сервера:**
   ```javascript
   refreshGroqModels();
   refreshOpenRouterModels();
   ```

2. **Периодически (каждые 8 часов):**
   ```javascript
   setInterval(refreshGroqModels, 8 * 60 * 60 * 1000);
   setInterval(refreshOpenRouterModels, 8 * 60 * 60 * 1000);
   ```

### Ручной запуск

Для ручного запуска синхронизации можно:
1. Перезапустить сервер
2. Добавить API эндпоинт для ручного триггера (не реализовано по умолчанию)

При синхронизации в консоль выводится:

**Успешная синхронизация:**
```
Обновляем список GROQ моделей...
GROQ синхронизирован: 3 новых добавлено, 1 устаревших отключено.
```

**Ошибки:**
```
⚠️ GROQ сервис не настроен, обновление моделей пропущено.
Ошибка автообновления GROQ: Network timeout
```

## Настройка

### Отключение синхронизации

Чтобы отключить синхронизацию для провайдера:

1. **Groq:** Не указывайте `GROQ_API_KEY` в `.env`
2. **OpenRouter:** Закомментируйте вызовы `refreshOpenRouterModels()` в `server.js`

### Изменение периодичности

Измените интервал в `server.js`:

```javascript
// Вместо 8 часов (8 * 60 * 60 * 1000)
setInterval(refreshGroqModels, 24 * 60 * 60 * 1000); // Каждые 24 часа
```

## Технические детали

### Функции в коде

- `refreshGroqModels()` — строки 2112-2174 в `server.js`
- `refreshOpenRouterModels()` — строки 2176-2243 в `server.js`
- `loadModels()` — загрузка из `available-models.json`
- `saveModels()` — сохранение в `available-models.json`

### Формат ID моделей

Внутренний ID формируется по правилам:
- **Groq:** `groq-{model_id}` (например, `groq-llama-3.1-8b`)
- **OpenRouter:** `or-{model_id}` с заменой `:` на `-` (например, `or-openai-gpt-3.5-turbo-free`)

Это позволяет избежать конфликтов между провайдерами и обеспечивает уникальность ID.

## Troubleshooting

### Проблема: Модели не синхронизируются

**Решение:**
1. Проверьте наличие API ключа для Groq (`GROQ_API_KEY`)
2. Проверьте доступность API провайдера
3. Проверьте логи сервера на наличие ошибок

### Проблема: Модели дублируются

**Решение:**
Проверьте формат ID в `available-models.json`. ID должны быть уникальными и соответствовать формату `{provider}-{model_id}`.

### Проблема: Ручные настройки теряются

**Решение:**
Это не должно происходить. Если настройки теряются, проверьте:
1. Правильность формата ID модели
2. Соответствие `provider` в локальной модели и в API ответе
3. Логи синхронизации на наличие ошибок
